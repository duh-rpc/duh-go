Errors from a HandleBytes content endpoint

You serve raw content — a file, an image, an HTML page — through HandleBytes. When your handler fails before it writes the first byte, the client now gets your real HTTP status and a decodable error body. No more 455 swallowing your 404.

This is a behavior change for anyone writing content endpoints with duh.HandleBytes. Nothing in your handler signature changes — you write the same three-argument handler you always did. What changed is what the client receives when that handler returns an error early. This guide is written for you, the handler author: what you send, what your client gets back, and one new trick for custom error pages.

What you hand in, what the client gets back

Your side — the handler you write

Return nil and the bytes you wrote become a 200. Return an error before writing anything, and DUH turns it into a standard Reply for the client.

DUH's job (you don't call this)

Pick an encoding the client's DUH client can actually decode, write the status and the Reply body, set the service headers. This is the part that changed.

A content endpoint's success responses use the content's own media type — application/octet-stream, image/png, text/html. That is what the client puts in its Accept header. But none of those media types can carry a structured error Reply. So when your handler errors before producing content, DUH has to answer in something the client can decode instead.

The change, in one before/after

Say your handler serves images and the client requested Accept: image/png. Your handler can't find the record, so it returns a 404.

Before — the bug

// client: Accept: image/png
// handler: return 404

HTTP/1.1 455 ...
# "image/png is not supported,
#  only [json, protobuf]"
# your 404 is gone.

After — the fix

// client: Accept: image/png
// handler: return 404

HTTP/1.1 404 Not Found
Content-Type: application/json

{"code":"404","message":"..."}
# real status + decodable body.

Before, DUH tried to encode the error in the client's Accept media type, failed (you can't put a Reply in a PNG), and returned 455 Unsupported Media Type — masking the 404 you actually returned. Now the pre-body error falls back to JSON, which every DUH client links and can always decode. Your status survives.

Why JSON works everywhere The DUH client decodes an error by the response's Content-Type, and it always links the JSON codec. So a JSON error body is universally decodable regardless of what the client asked for. That is why JSON is the fallback.

The rules you can rely on

Given a pre-body error (your handler returns non-nil before the first Write):

Client sendsClient gets the error as
Accept: application/octet-stream / image/png / text/html / emptyJSON — the universal fallback
Accept: application/jsonJSON
Accept: application/protobufProtobuf — explicit opt-in
any Content-Type on the requestignored — does not affect error encoding

Two rules are worth committing to memory:

1. Protobuf only when the client explicitly asks for it

The error is JSON unless the client sets Accept: application/protobuf. That's the only way to get a protobuf error Reply.

2. The request Content-Type never decides the error encoding

Content-Type describes the body the client sent you (e.g. the blob it's uploading). Accept describes the response it wants. Only Accept is consulted. If you relied on "I uploaded protobuf, so I'll get a protobuf error" — that never was a sound assumption, and it's now explicitly gone.

If you tracked the original ticket The first acceptance criterion — "request Content-Type: protobuf → protobuf error" — was itself the bug. Error encoding is negotiated by Accept only. 455 is now reserved for a structured endpoint receiving a success Accept it genuinely cannot satisfy — never for a content-endpoint error.

New: render your own error page

Sometimes you don't want a JSON Reply at all — you want an HTML error page, or a redirect, or some bespoke body. You can, because HandleBytes defers the status line until your first write. The move: write your own response, then return nil. Returning nil tells HandleBytes you've already answered, so it won't also send a Reply. 

func(w http.ResponseWriter, r *http.Request) {
    duh.HandleBytes(w, r, func(r *http.Request, bw duh.BytesWriter) error {
        rec, err := store.Find(r.Context(), id)
        if err != nil {
            // Render your own error straight to w and claim the status.
            w.Header().Set("Content-Type", "text/html; charset=utf-8")
            w.WriteHeader(http.StatusNotFound)
            _, _ = w.Write([]byte("<html><body>not found</body></html>"))
            return nil   // nil == "I answered; don't send a Reply"
        }
        _, err = bw.Write(rec.Bytes)
        return err
    })
}
One response only Write your own response or return an error — never both. If you write a full response and also return a non-nil error, two responses get written. The contract: return nil when you've handled it yourself; return a non-nil error only to get the standard Reply.
Custom status needs the raw writer To set a status other than 200, write to the http.ResponseWriter (w) you already hold in the closure, as above. Writing through bw (the BytesWriter) commits 200 on the first write — that's the success path, not the error path.

Why there's no override hook anymore

A previous iteration exposed a package-level ReplyContentError variable you could reassign to customize error rendering globally. That's gone, replaced by the return-nil pattern above. Two reasons, both about your safety:

It was a data race

A mutable package var reassigned at startup and read on every request is a race the detector flags. A plain function has no such hazard.

It leaked globally

Reassigning it changed error rendering for every content endpoint in the process. Per-endpoint customization now lives in the one handler that wants it — where it belongs.

duh.ReplyContentError still exists as a regular exported function you can call, but it is no longer a variable and cannot be reassigned. If you need custom error output, render it in your handler and return nil.
